# 原尺寸 p6 表面冷编译触及云端内存上限

为了检查原尺寸边界积分能否进入实际计算，本次尝试把一个 top/x 表面形式编译成可执行内核。原始 AUTO 清单保持 32,060 个模式，由清单确定的求积 degree 保持 160。18 个六面体只用于边界与编译检查，不能充当精度合格网格。

| 实测项目 | 结果 |
|---|---:|
| 18-cell p6 空间及双向 Floquet MPC | 构造完成，单元维数 882 |
| 冷编译形式 | 一个生产 top/x 形式，degree160 |
| 监督耗时 | 75.948353 s |
| 采样同时进程树峰值 RSS | 3,247,665,152 B |
| 预设内存上限 | 3,221,225,472 B（3 GiB） |
| swap / 后代清理 | 0 / 全部清理 |
| 退出分类 / leader exit | RESOURCE_CONTROLLED_STOP / −9 |
| C 源文件 / 临时 C 文件 | 均为 0 B，已原样保留 |
| 编译二进制、表面向量及独立求积比较 | 均未产生 |

采样峰值超过预设上限约 26.44 MB，监督器终止了完整子进程树。编译前的准入估算为 2,327,080,960 B，其中编译器工作空间只是保守预测，不是证明过的上界；这次实测说明该估算不足以保证此冷编译在 3 GiB 内完成。没有把退出 −9 解释成内核 OOM，也没有据此断言工作站无法计算目标模型。

302 次资源采样中，外部编译器子进程计数最大为 0，仅观察到 Python 进程。峰值由 Python worker 3,147,558,912 B 与监督进程 100,106,240 B 构成。结合零字节 C 文件，停止位置在 Python 侧 UFL/FFCx/Basix 的准备过程中，尚未观察到外部 C 编译；具体内部函数或数组的分配来源尚未实测。
